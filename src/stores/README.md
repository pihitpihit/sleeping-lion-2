# 스토어 규약 (Zustand)

이 디렉토리에는 스토어를 두지 않는다. 규약만 적어둔 자리다.

## 어디에 두는가

**스토어는 그것을 쓰는 기능 폴더 안에 둔다.** SPEC 4.1의 기능별 분리를 따른다.

```
src/features/satchel/store/layoutStore.ts     ← 이렇게
src/stores/layoutStore.ts                     ← 이렇게 하지 않는다
```

전역 스토어 디렉토리를 만들면 서로 무관한 상태가 한곳에 쌓이고, 어느 기능이
무엇을 쓰는지 알 수 없게 된다. 두 기능이 같은 스토어를 봐야 할 때가 오면 그때
공용 위치를 만든다.

## `persist` 미들웨어 — 붙여도 되는 곳과 안 되는 곳

**SPEC 5.2가 정본이다.** 축 ②(행낭)의 상태는 두 성격으로 갈리고, 저장 여부가
반대다.

| 스토어 성격 | 예 | `persist` |
|---|---|---|
| **사용자 설정** | 위젯 배치, 툴바 위치 | **붙인다** (`localStorage`) |
| **도구 런타임** | 뽑은 보정 카드, 원소 하강 상태, 주도권 입력값 | **금지** |

도구 런타임 상태는 **새로고침하면 초기화되는 것이 의도된 동작**이다. 편의를
위해 persist를 붙이고 싶어지는 순간이 오겠지만, 그러면 축 ②가 축 ①처럼
변해버린다.

## 어느 쪽에도 IndexedDB와 서버 동기화는 없다

`localStorage`를 쓰는 것은 용량이 작아서가 아니라 **성격이 다르다는 신호**다.
Dexie 테이블에 넣으면 나중에 동기화 대상 목록에 자연스럽게 섞여 들어간다.
축 ①(캠페인 기록지)의 것과 물리적으로 다른 곳에 둔다.

## 도메인 로직은 스토어 밖에 둔다

SPEC 4.1은 도메인 로직을 UI에서 분리해 Vitest로 검증하라고 한다. 스토어도
UI 쪽이다.

격자 계산, 배치 유효성 판정, 열 수 변화 파생 같은 것은 **순수 함수로 따로 두고**
스토어는 그 함수를 부르기만 한다. 그래야 테스트에 React도 브라우저도 필요 없다.
