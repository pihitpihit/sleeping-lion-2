# M3 — 레이아웃 모델과 영속  ✅ 완료 (2026-07-31)

무엇이 어디에 놓였는지를 자료구조로 정하고, 새로고침을 견디게 만든다.

**여기가 SPEC 5.2와 부딪히는 지점이다.** [결정 1](../README.md#결정-1--레이아웃은-영속-위젯-내부-상태는-휘발)을
먼저 읽고 시작한다.

**선행:** M2 (격자 계산, 유효성 판정)
**예상 산출물:** `src/features/satchel/layout/` — 타입, 저장소, 파생 규칙, 테스트

---

## T3.1 — 자료구조

```ts
/** 보드에 놓인 위젯 하나. */
interface WidgetInstance {
  instanceId: string   // 같은 종류를 여러 개 놓을 수 있으므로 정의 id와 별개
  definitionId: string // 'test' 등 레지스트리 키
  x: number; y: number // 좌상단 셀 좌표
  w: number; h: number // 셀 단위 크기
}

/** 한 열 수에 대한 배치 목록. */
interface Layout {
  columns: number
  widgets: WidgetInstance[]
}

/** localStorage에 실제로 들어가는 것. */
interface SatchelSettings {
  version: number
  layouts: Record<number, Layout>  // 키는 열 수
  toolbarPosition: 'top' | 'left'  // M5
}
```

- [x] 타입 정의
- [x] `instanceId` 생성 방법을 정한다. **`Math.random()`과 `Date.now()`를 쓸 수 있는
      환경인지 확인할 것** — 브라우저 런타임이므로 문제없지만, 테스트에서 결정적
      값이 필요하면 생성기를 주입 가능하게 만든다. `crypto.randomUUID()`를 기본으로.

**행 수를 저장하지 않는 이유:** 행 수는 높이에서 파생되고 툴바 위치에 따라서도
변한다. 저장하면 실제와 어긋난 값이 남는다. 열 수만이 안정적인 키다.

## T3.2 — localStorage 저장소

- [x] 읽기/쓰기 래퍼. 키는 `sl2.satchel.v1` 같은 이름 공간을 준다.
- [x] **읽기는 절대 던지지 않는다.** JSON 파싱 실패, 스키마 불일치, 저장소 접근 거부
      (사파리 프라이빗 모드)를 전부 흡수하고 기본값을 낸다. 도구 화면이 저장소 문제로
      안 뜨면 안 된다.
- [x] 쓰기 실패도 흡수한다. 용량 초과나 접근 거부 시 조용히 넘어가되, 개발 중에는
      알 수 있게 한 번만 경고를 남긴다.
- [x] 쓰기를 묶는다. 드래그 중에 매 프레임 저장하면 안 된다 — **조작이 끝날 때만**
      저장한다(M6의 제스처 종료 시점).

**수용 기준:**
- 저장소에 쓰레기 문자열을 넣어도 앱이 기본 레이아웃으로 뜬다
- `localStorage`를 막아도 앱이 동작한다(배치가 유지되지 않을 뿐)
- 위젯 하나를 옮기고 새로고침하면 그 자리에 있다

## T3.3 — 버전과 마이그레이션

지금은 v1뿐이지만 자리를 미리 만든다. 나중에 필드를 바꿀 때 사용자의 배치를
날리지 않기 위해서다.

- [x] `version` 필드를 읽고 알 수 없는(더 높은) 버전이면 **건드리지 않고 기본값으로
      동작한다.** 덮어쓰면 다른 기기에서 최신 버전을 쓰던 사용자의 데이터가 깨진다.
- [ ] **하지 않음.** 마이그레이션 함수 테이블은 만들지 않았다. v1뿐이라 상위 버전
      방어(건드리지 않고 기본값)만 넣었다. v2가 생길 때 추가한다.
- [x] 알 수 없는 `definitionId`가 들어있으면 그 위젯만 버리고 나머지는 살린다.
      레지스트리에서 위젯을 제거했을 때 전체 레이아웃이 죽으면 안 된다.

**수용 기준:** 저장된 데이터에 존재하지 않는 위젯 id를 섞어 넣어도 나머지 배치가
정상으로 뜬다.

## T3.4 — 열 수 변화 대응 (파생 규칙)

[결정 3](../README.md#결정-3--열-수마다-레이아웃을-따로-둔다)의 구현.

처음 보는 열 수로 들어왔을 때:

- [x] 저장된 레이아웃 중 **열 수가 가장 가까운 것**을 고른다. 동률이면 작은 쪽 —
      넓은 배치를 좁은 격자에 넣는 것보다 반대가 안전하다.
- [x] 좌표를 비율로 옮긴다: `newX = round(oldX * newColumns / oldColumns)`
- [x] 크기도 같은 비율로 옮기되 **최소 크기 이하로 줄어들지 않게** 한다(M4의 위젯
      정의가 최소 크기를 갖는다).
- [x] 옮긴 결과가 격자를 벗어나거나 서로 겹치면 **겹치는 것부터 `findFreeSpot`으로
      재배치**한다. 자리가 없으면 그 위젯은 배치하지 않고 목록에서 뺀다.
- [x] 파생 결과를 새 열 수의 레이아웃으로 저장한다. 이후로는 독립적으로 편집된다.
- [x] 저장된 레이아웃이 하나도 없으면 빈 레이아웃에서 시작한다.

**이 로직이 이번 마일스톤에서 가장 까다롭고 가장 조용히 틀리는 부분이다.**
반드시 순수 함수로 만들고 테스트를 촘촘히 붙인다.

**수용 기준 (테스트):**
- 4열 → 8열 파생 시 위젯이 겹치지 않고 전부 격자 안에 있다
- 8열 → 4열 파생 시 최소 크기가 지켜진다
- 자리가 부족하면 일부가 빠지되 남은 것들은 유효하다
- 파생은 원본 레이아웃을 변형하지 않는다(불변)

## T3.5 — 레이아웃 스토어 (Zustand)

- [x] 현재 열 수에 해당하는 레이아웃을 노출
- [x] 조작: 위젯 추가, 제거, 이동, 크기 변경
- [x] 모든 조작은 **유효성 검사를 통과한 것만 반영**한다. 잘못된 배치를 스토어에
      넣고 나중에 화면에서 거르면 저장소에도 잘못된 값이 들어간다.
- [x] `persist` 미들웨어를 쓸지 직접 구독해 저장할지 정한다. 열 수별 레이아웃을
      부분 갱신해야 하므로 **직접 구독**이 단순할 수 있다.
- [x] **도구 런타임 상태는 이 스토어에 넣지 않는다.** 위젯 내부 상태는 각 위젯이
      자기 메모리 스토어를 갖는다(M4).

**수용 기준:** 격자 밖으로 나가는 이동이나 겹치는 배치를 스토어가 거부한다.

## 열린 질문

1. 같은 종류의 위젯을 여러 개 놓는 것을 허용할지. 자료구조는 허용하도록 잡았지만
   위젯 정의에 `maxInstances`를 두는 편이 나을 수 있다(원소 트래커가 둘일 이유는
   없다). M4에서 결정.
2. 툴바 위치가 바뀌면 보드 크기가 달라져 행 수가 변한다. 행이 줄어 위젯이 격자
   밖으로 나가는 경우 — 파생 규칙을 열 수뿐 아니라 행 수에도 적용해야 하는가.
   보드가 스크롤되지 않으므로 무시할 수 없는 경우다.
3. 배치 초기화(전부 지우기) 기능을 M5 햄버거 메뉴에 넣을지.
