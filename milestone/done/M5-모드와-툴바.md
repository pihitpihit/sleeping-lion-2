**예상 산출물:** `src/features/satchel/mode/`, `src/features/satchel/toolbar/`

## 모드 정의

| | 플레이 모드 | 편집 모드 |

## T5.2 — 툴바 위치와 기기별 기본값

요구사항: 상단/좌측을 설정으로 바꿀 수 있고, 기기 유형에 따라 기본값이 다르다.

### 기본값 규칙

> **M2 실측이 애초 근거를 무너뜨렸다.** 계획서는 "폰 가로에서 상단 툴바면 행이
> 1~2개로 줄어든다"고 보고 좌측 기본값의 근거로 삼으려 했다. 실제로 재보니
> **상단 9×3, 좌측 8×3으로 행 수가 같다.** 좌측은 열을 하나 줄이는 대신 셀을
> 키우는(81→86px) 맞바꿈일 뿐이다. 근거를 다시 세워야 한다.

세로 공간이 귀한 화면일수록 툴바를 옆으로 돌린다 — 는 **격자 칸 수로는 정당화되지
않는다.** 대신 다음 근거로 정한다.

| 조건 | 기본 위치 | 이유 |
|---|---|---|
| 세로 방향이고 폭 < 768px | **상단** | 폰 세로는 폭이 귀하다. 좌측 툴바는 격자 열을 통째로 잡아먹는다 |
| 가로 방향이고 높이 < 500px | **좌측** | 칸 수 때문이 아니라 **손 위치** 때문이다. 폰을 가로로 들면 엄지가 좌우 가장자리에 놓이고 상단은 멀다 |
| 그 외(태블릿·데스크톱) | **좌측** | 세로가 넉넉하고, 위젯이 늘면 툴바 항목도 늘어 세로로 쌓는 편이 낫다 |

**T2.4의 표를 근거로 다시 확인할 것.** 툴바 위치를 바꿔도 격자가 크게 달라지지
않으므로, 이 결정은 성능이 아니라 **조작 편의**의 문제다. 실기 확인(M7 T7.7)에서
뒤집힐 수 있다.

- [x] 판정 함수를 순수 함수로 뽑는다 (`defaultToolbarPosition(viewport) => 'top' | 'left'`)
- [x] **기기 종류(User-Agent)로 판단하지 않는다.** 뷰포트 크기와 방향으로만 정한다.
      UA 판별은 틀리고 낡는다. 아이패드가 데스크톱 UA를 보내는 문제도 있다.
- [x] 사용자가 한 번이라도 직접 고르면 그 값이 이긴다. 이후 회전해도 바뀌지 않는다 —
      기본값이 계속 덮어쓰면 설정이 무의미해진다.
- [x] M2의 T2.4 실측 결과(폰 가로에서 상단 툴바 시 행 수)로 이 표를 검증한다

**수용 기준:**
- 폰 세로에서 상단, 폰 가로에서 좌측으로 열린다
- 직접 좌측으로 바꾼 뒤 회전해도 좌측을 유지한다
- 툴바 위치가 바뀌면 보드 크기가 바뀌고 격자가 다시 계산된다(M1의 ResizeObserver)

## T5.3 — 툴바 셸

- [x] 상단/좌측 두 방향을 같은 컴포넌트로 그린다. 방향은 CSS로 처리하고 마크업을
      복제하지 않는다.
- [x] 안전 영역 처리 — 좌측 툴바는 `env(safe-area-inset-left)`, 상단은 `-top`
- [x] 터치 목표 크기를 확보한다. 버튼 최소 44px. 플레이 중 급하게 누르는 화면이다.
- [x] 툴바가 보드 영역을 침범하지 않게 한다 — 겹치면 위젯이 가려진다

## T5.5 — 편집 모드 툴바

- [x] 햄버거 버튼
- [x] 플레이 모드 전환 버튼
- [x] 위젯 목록 — 레지스트리를 훑어 버튼을 만든다
  - `maxInstances === 1`인 정의는 **토글**(켜짐/꺼짐 상태 표시)
  - 그 외는 **추가 버튼**(누를 때마다 하나 더)
  - 이 구분이 눈에 보여야 한다(M4의 T4.4 참조)
- [x] 자리가 없어 추가할 수 없을 때 알린다
- [x] 위젯이 많아지면 툴바가 넘친다 — 가로 스크롤 또는 접기. **보드를 밀어내지
      않는 방식**으로 처리한다

## T5.6 — 햄버거 메뉴

두 모드 공통. 자주 쓰지 않는 것들을 넣는다.

- [x] 웰컴으로 돌아가기 (M1의 열린 질문 2를 여기서 닫을 수 있다)
- [x] 툴바 위치 바꾸기 (상단/좌측)
- [x] 배치 초기화 — **되돌릴 수 없으므로 확인을 받는다**
- [x] 열림/닫힘, 바깥 누르면 닫기, `Esc`로 닫기
- [ ] **하지 않음.** `Esc`와 바깥 누르기로 닫는 것까지만 했다. 초점 가두기는
      항목이 셋뿐이라 급하지 않지만 접근성상 남은 빚이다.

## T5.7 — 모드에 따른 보드 반응

- [x] 편집 모드에서만 격자를 그린다. 격자는 **배경 레이어**이고 위젯 아래에 깔린다.
- [x] 편집 모드에서 위젯 내부 상호작용을 막는다. 컨테이너에 `pointer-events: none`을
      위젯 내용에만 걸고 컨테이너 자신은 제스처를 받는다(M6).
- [x] 모드 전환에 짧은 전환 효과. `prefers-reduced-motion` 존중.

**수용 기준:**
- 플레이 모드에서 격자가 보이지 않는다
- 편집 모드에서 위젯 안의 버튼을 눌러도 반응하지 않는다
- 플레이 모드에서 위젯 안의 버튼이 정상 동작한다

   **명시적으로 편집 버튼을 눌러야 한다.** 플레이 중 오조작 위험이 크다.

   `'auto' | 'top' | 'left'` 세 가지이고 기본은 `'auto'`다. 메뉴에서 한 번 누를
   때마다 자동 → 위 → 왼쪽 → 자동 으로 돈다. 2단 토글이면 한 번 고정한 뒤
   자동으로 되돌아갈 방법이 없었다.
3. ~~되돌리기(undo)가 필요한가~~ → **넣었다** (2026-07-31 결정). 편집 모드 툴바의
   되돌리기 버튼과 `Ctrl/Cmd+Z`. 이력은 최대 20단계이며 메모리에만 둔다 —
   지금 편집 중인 것에 대한 상태지 설정이 아니다. 격자가 바뀌면(회전·툴바 이동)
   이력을 버린다. 다른 격자에서 만든 배치로 되돌리면 좌표가 맞지 않는다.
