# N2 — PocketBase 기반

**여기부터 라즈베리파이가 필요하다.** 스키마·접근 규칙·HTTPS를 세우고, N1이 만든
빈 세션 자리에 진짜 인증을 끼운다.

선행: N1 · 정본: [`../SPEC.md`](../SPEC.md) 4.2 / 6.1 · 전체 그림: [N0](./N0-네트워킹-설계.md)

---

## 목표

1. 라즈베리파이에서 PocketBase가 **HTTPS로** 뜬다.
2. 계정·파티·전투 스키마가 마이그레이션 파일로 관리된다.
3. **접근 규칙이 서버에서 강제된다.** 클라이언트를 우회해도 남의 것이 안 보인다.
4. N1의 세션 자리에 PocketBase SDK가 들어간다.

---

## 왜 서버 규칙이 전부인가

레포와 번들이 공개다. 누구든 번들을 읽고 API를 직접 두드릴 수 있다. **클라이언트의
게이트는 "안 보여주기"일 뿐이고, "안 주기"는 서버만 할 수 있다.**

그래서 이 마일스톤의 진짜 산출물은 화면이 아니라 **규칙 표**다. 각 컬렉션마다
누가 무엇을 할 수 있는지 적고, 그것을 그대로 시험한다.

---

## 할 일

### 서버 세우기

- [ ] PocketBase 단일 바이너리 구동. 재부팅 후 자동 시작(systemd).
- [ ] **HTTPS.** PWA와 보안 쿠키가 요구한다. Cloudflare Tunnel이면 인증서와 집 IP
      노출을 한 번에 해결한다 — 가정용 회선의 포트를 여는 것보다 낫다.
- [ ] 관리자 계정 보호. 관리 화면을 공개 경로에 두지 않는다.
- [ ] **백업.** SQLite 파일을 주기적으로 복사한다. 동기화가 붙으면 서버가 유일한
      사본이 되는 순간이 오고, 그때가 위험하다.
- [ ] 운영 문서를 남긴다 — 어디에 무엇이 있고, 죽으면 어떻게 살리고,
      **비밀번호 분실 시 관리자가 어떻게 바꿔주는지.** SMTP가 없어 재설정 메일이
      나가지 않으므로 이것은 기능이 아니라 절차다.

### 스키마

레코드 단위와 이름만 정하고, 필드는 각 마일스톤에서 채운다.

- [ ] `users` — PocketBase 기본. 이메일 대신 아이디로 로그인.
- [ ] `parties` — 이름, 만든 사람, 만든 때.
- [ ] `party_members` — 파티 × 사용자. **한 사람이 여러 파티에 속한다.**
- [ ] `invites` — 파티, 토큰, 만든 사람, 만료, 취소 여부, 쓴 횟수.
- [ ] `battles` — 파티, 연 사람, 연 때, 끝난 때.
- [ ] `battle_participants` — 전투 × 사용자.
- [ ] `battle_state` — 전투당 하나. 축 ②의 내부 상태를 담는다. **작다** —
      원소 여섯 값이 전부다.
- [ ] 마이그레이션 파일로 버전 관리. 손으로 만든 스키마는 재현되지 않는다.

### 접근 규칙 — 이 마일스톤의 핵심

각 컬렉션에 대해 **표로 먼저 적고** 그대로 옮긴다.

- [ ] 로그인하지 않으면 **아무것도** 못 읽는다.
- [ ] 파티는 **속한 사람만** 읽는다.
- [ ] 초대는 **토큰을 아는 사람만** 쓸 수 있고, 목록으로는 못 읽는다.
- [ ] 전투는 **그 파티 사람만** 읽는다.
- [ ] `battle_state`는 **그 전투 참여자만** 읽고 쓴다.
- [ ] 남의 파티 id를 넣어 만들기를 시도하면 막힌다.

### 클라이언트 붙이기

- [ ] PocketBase JS SDK 도입. N1이 만든 세션 경계 안쪽만 갈아끼운다.
- [ ] 서버 주소는 `VITE_*`로. **공개 빌드에는 들어가지 않는다**(N1의 플래그와 함께).
- [ ] 토큰 갱신은 **틈틈이, 실패해도 조용히.** 갱신 실패로 로그아웃시키면
      오프라인에서 앱이 닫힌다.
- [ ] 401을 만나면 그때 세션을 버린다. 네트워크 오류와 구별한다 — 신호가 없는
      것과 쫓겨난 것은 다르다.

---

## 검증

- [ ] 로그인하지 않은 채 API를 직접 호출하면 전부 거부된다. **브라우저가 아니라
      `curl`로** 확인한다 — 화면을 안 거치는 것이 요점이다.
- [ ] 다른 파티 사람의 토큰으로 남의 파티를 읽으면 거부된다.
- [ ] 전투 참여자가 아닌 사람이 `battle_state`를 쓰면 거부된다.
- [ ] 서버를 끄고 앱을 열면 **저장된 세션으로 열린다.**
- [ ] 공개 빌드 번들에 서버 주소가 없다(`grep`).

## 열린 질문

- **PocketBase로 갈 것인가, 관리형 백엔드로 갈 것인가.** SPEC 4.2는 PocketBase를
  확정으로 적었으나, 그 뒤 "우리가 돌볼 기계가 없었으면" 하는 요구가 나왔다.
  2026-08-01 기준으로 찾아본 것:

  | | Cloudflare Workers | Supabase |
  |---|---|---|
  | 무료 | 요청 10만/일, Durable Objects 됨(SQLite) | DB 500MB, 실시간 200만 메시지/월, MAU 5만 |
  | 미사용 시 일시정지 | 없음 | **1주일** |
  | 유료 시작 | $5/월 | $25/월 |
  | 인증·DB·접근규칙 | **직접 만들어야** | 내장(GoTrue·Postgres·RLS) |

  우리 부하는 한 판에 메시지 2,000건, 동시 연결 4개, 저장은 메가바이트 단위다.
  **어느 쪽이든 무료 한도의 1%도 안 쓴다.** 고르는 기준은 요금이 아니라 *무엇을
  직접 만들어야 하는가*와 *일시정지를 견딜 수 있는가*다.

  Supabase는 PocketBase와 개념이 거의 1:1이라(API 규칙 → RLS 정책) 이 문서의
  스키마와 규칙 표가 그대로 옮겨간다. 일시정지는 GitHub Actions 주간 핑으로
  완화되나 부품이 하나 는다.

  **Supabase의 Broadcast는 DB에 쓰지 않고 메시지만 흘려보낸다.** SPEC 5.4의
  "전투가 끝나면 어느 기기에도 남지 않는다"와 더 잘 맞는다 — PocketBase는
  공유하려면 일단 저장해야 해서 절충으로 남겨둔 부분이다.

- **anon 키는 공개해도 된다.** Supabase 문서가 명시한다("Safe to expose online:
  web page… source code"). 보호는 RLS가 한다. **그러면 SPEC 3.1의 "공개 번들에
  서버 주소가 들어가지 않는다"는 근거가 사라진다** — 그 규칙은 집 서버 주소를
  감추려던 것이었다. 딸린 결정("정식을 열면 GitHub Pages를 내린다")도 함께
  재고한다.
- **`service_role` 키는 절대 클라이언트에 넣지 않는다.** RLS를 우회한다.
- **RLS를 안 켠 테이블은 anon 키만으로 통째로 열린다.** 이 마일스톤에서 가장
  조심할 곳이다.
- 토큰 수명과 N1의 세션 만료를 어떻게 맞출 것인가.
- 라즈베리파이 한 대가 감당할 동시 접속 수. Realtime은 연결을 붙잡고 있으므로
  파티 몇 개까지 열어줄지 판단해야 한다 — N3의 초대 정책과 직결된다.
