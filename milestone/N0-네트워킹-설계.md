# N0 — 네트워킹 설계 (정본)

로그인·파티·전투·실시간 공유의 **전체 그림**이다. N1~N5는 이 문서를 나눠 담은
것이므로, 개별 문서가 헷갈리면 여기로 돌아온다.

설계 정본은 [`../SPEC.md`](../SPEC.md) 3.1 / 5.4 / 6.1 / 6.2이며 이 문서는 그것을
구현 단위로 푼 것이다.

---

## 무엇을 만드는가

세 겹이다. **아래가 없으면 위가 못 선다.**

```
   전투(battle)      이번 판에 모인 사람들. 끝나면 사라진다.
        │             └ 축 ②의 내부 상태를 참여자끼리 공유
   파티(party)       같이 노는 사람들. 지속된다.
        │             └ 누구나 만들고 누구나 초대(링크)
   계정(user)        로그인. 이게 없으면 아무것도 못 쓴다.
```

그리고 이 셋과 **나란히 있되 섞이지 않는 것**이 하나 더 있다.

```
   행낭 설정          위젯 배치·툴바 위치. 각자 localStorage. 공유하지 않는다.
```

행낭을 열면 **여전히 자기 배치가 열린다.** 공유되는 것은 원소 상태 같은 내부
값뿐이다. 남의 배치가 내 화면을 덮으면 도구가 아니라 방해물이 된다.

---

## 순서와 이유

| # | 문서 | 서버 필요 | 왜 이 순서인가 |
|---|---|---|---|
| N1 | 로그인 게이트와 두 배포 | ✗ | 서버 없이 만들 수 있다. 게이트를 먼저 세워야 그 뒤 화면들이 "로그인된 상태"를 전제로 설계된다 |
| N2 | 백엔드 기반 (Supabase) | ✓ | 스키마·RLS 정책. 여기부터 서버가 필요하다 |
| N3 | 파티와 초대 링크 | ✓ | 전투는 파티 안에서 열리므로 먼저 |
| N4 | 전투 세션 | ✓ | 방을 만들고 알리고 참여시킨다. 아직 공유하는 값은 없다 |
| N5 | 원소 트래커 실시간 공유 | ✓ | 빈 방에 첫 값을 넣는다 |

**N4까지 만들고 N5에서 값을 얹는 순서가 중요하다.** 방과 값을 같이 만들면
"안 맞는 것이 방 문제인지 값 문제인지" 가릴 수 없다. N4가 끝나면 참여자 목록이
실시간으로 늘고 주는 것만으로 배관이 검증된다.

---

## 절대 지킬 것

**1. 로그인 게이트가 offline-first를 깨면 안 된다.**

게이트의 기준은 *서버에 닿는가*가 아니라 **이 기기에 유효한 세션이 있는가**다.
첫 로그인만 네트워크를 요구한다. 매 실행마다 서버에 물으면 신호 없는 자리에서
앱이 통째로 멈춘다 — 글룸헤이븐은 지하에서 세 시간씩 하는 게임이다.

**2. 전투가 끊겨도 판은 멈추지 않는다.**

혼자 모드로 강등하고 로컬로 계속 쓴다. 돌아올 때 서버와 다르면 한 번 묻는다.
원소는 값이 여섯 개뿐이라 이 정도로 충분하다.

**3. 클라이언트의 게이트는 UX일 뿐이다.**

레포와 번들이 공개다. 화면을 가리는 것은 아무것도 막지 못한다. **강제는 전부
Supabase RLS 정책에서** 이뤄진다. 클라이언트는 "안 보여주기", 서버는 "안 주기".
N2에서 정책을 짤 때 이것을 기준으로 삼는다.

**RLS를 켜지 않은 테이블은 `anon` 키만으로 통째로 열린다.** 정책을 쓰는 것보다
RLS를 켜는 것이 먼저다.

**4. 저작권 경계를 넘지 않는다.**

공유되는 것은 원소 6개의 3단계 상태, 주도권 숫자, 보정 카드의 **식별자**뿐이다.
전부 순수 수치라 SPEC 3장의 서버 경계 안이다. **카드 원문은 어느 층에도 올리지
않는다.**

**5. 시험판은 진짜 데이터에 닿지 못한다.**

`mock` 번들에는 서버로 나가는 길이 아예 없어야 한다. 빌드 시점에 가른다(N1).

> **2026-08-05 개정.** 이 항목은 원래 "**공개 배포에는 서버 주소가 들어가지
> 않는다**"였고, 근거는 집 서버 주소를 감추려는 것이었다. 백엔드가 Supabase로
> 정해져 그 근거가 사라졌다 — 주소와 `anon` 키는 공개해도 되는 값이다. **가른다는
> 결론은 남고 이유가 바뀌었다.** 대신 **`service_role` 키는 어느 번들에도 넣지
> 않는다** — 그것은 RLS를 우회한다.

**6. 우리가 돌볼 서버를 두지 않는다.**

기계도, VPS도, 컨테이너도 우리 손으로 돌리지 않는다. 서버 쪽 필요는 **관리형
서비스로만** 채운다. 자가호스팅은 되돌아갈 길로도 두지 않는다.

이 정책이 백엔드를 고른 축이다(SPEC 4.2). N2~N5에서 서버가 얽힌 결정이 나올
때마다 여기로 돌아온다. **무료 등급의 제약을 우리가 만든 부품으로 메우는 것보다
유료 등급이 정책에 맞는다** — 부품은 조용히 고장나고, 고장난 것을 알아채는 일까지
우리 몫이 된다.

## 아직 정하지 못한 것

여기 적힌 것은 **해당 마일스톤에 들어갈 때 정한다.** 미리 정하면 근거 없이
정하게 된다.

1. **초대 링크가 계정 생성까지 겸하는가.** 링크를 연 사람이 그 자리에서 가입까지
   하는 편이 메신저로 보내는 흐름에 맞는다. 다만 그러면 **링크 관리가 곧 서비스
   접근 통제**가 된다 — 링크가 퍼지면 이용자가 는다. 무료 등급이 감당할 범위와
   함께 정한다. (N3)
2. **전투 알림을 어디까지 보낼 것인가.** 앱이 열려 있을 때의 배너는 Realtime
   구독으로 된다. 앱이 닫힌 상태까지 알리려면 Web Push가 필요하고, iOS는 홈 화면
   추가와 권한 요청이 따라붙는다. 1단계는 배너만으로 두고 나중에 판단한다. (N4)
3. **전투의 수명.** 명시적 종료 버튼 + 무활동 자동 정리를 함께 둘 것으로 보이나,
   기준 시간은 실제로 한 판이 얼마나 걸리는지 보고 정한다. (N4)
4. **한 사람이 두 전투에 동시에 참여할 수 있는가.** 행낭의 내부 상태가 하나뿐이라
   막는 쪽이 자연스럽다. 여러 파티에 속하는 것은 허용하므로 알림은 여러 곳에서
   올 수 있다 — 어느 파티의 전투인지 보여줘야 한다. (N4)
5. **비밀번호 분실 대응.** SMTP가 없어 재설정 메일이 나가지 않는다. 관리자가
   콘솔에서 바꿔주는 운영 절차를 문서로 남긴다. (N2)
