# M6 — 배치 편집

편집 모드에서 위젯을 끌어 옮기고 격자에 맞춰 크기를 바꾼다.

**이 마일스톤이 가장 어렵다.** 제스처는 순수 함수로 뽑기 힘든 부분이 있으므로,
**판정 로직과 입력 처리를 분리**하는 데 특히 신경 쓴다.

**선행:** M5 (모드 전환)
**예상 산출물:** `src/features/satchel/interaction/` — 제스처 훅, 판정 로직, 테스트

---

## 설계

### 포인터 이벤트 하나로 통일

`mousedown`/`touchstart`를 따로 다루지 않는다. **Pointer Events**가 마우스·터치·펜을
한 경로로 처리한다. `setPointerCapture`로 요소 밖으로 나가도 추적을 유지한다.

### 드래그 중에는 상태를 저장하지 않는다

매 프레임 스토어를 갱신하면 렌더가 폭주하고 localStorage 쓰기가 쏟아진다.

- 드래그 중: **임시 시각 상태**(픽셀 오프셋)만 들고 위젯을 `transform`으로 움직인다
- 손을 떼는 순간: 셀로 환산 → 유효성 검사 → 통과하면 스토어에 반영 → 저장

### 겹침은 허용하지 않는다

[결정 2](./README.md#결정-2--격자-라이브러리를-쓰지-않고-직접-만든다)에 따라
밀어내기는 후순위다. 놓을 수 없으면 **원래 자리로 되돌린다.**

되돌리는 것이 조용하면 고장으로 보인다 — 놓을 수 없는 자리 위에 있을 때 **미리
시각적으로 알린다**(유효하지 않은 미리보기).

---

## T6.1 — 제스처 기반

- [ ] `onPointerDown`에서 `setPointerCapture`
- [ ] 이동/크기 조절을 구분하는 시작 지점 — 위젯 본체는 이동, 모서리 핸들은 크기
- [ ] **최소 이동 거리(임계값)를 둔다.** 손가락은 미세하게 흔들린다. 3~5px 이전에는
      드래그로 취급하지 않는다. 그래야 탭과 드래그가 구분된다.
- [ ] `touch-action: none`을 편집 모드의 위젯에만 건다. 플레이 모드에서 걸면
      화면 스크롤·확대가 막힌다.
- [ ] 포인터 취소(`pointercancel`) 처리 — 전화가 오거나 제스처가 가로채이면 원위치

---

## T6.2 — 이동

- [ ] 포인터 이동량을 위젯의 픽셀 오프셋으로 반영 (`transform: translate`)
- [ ] 오프셋을 셀로 환산해 **놓일 자리 미리보기**를 격자 위에 그린다
- [ ] 미리보기가 유효한지 실시간 판정 — 격자 안인가, 다른 위젯과 겹치는가
- [ ] 유효/무효를 색으로 구분 (테마 안에서 — 무효는 불씨색 `--sl-ember`)
- [ ] 손을 떼면 유효할 때만 확정, 아니면 원위치
- [ ] 확정 시 트랜지션으로 스냅 (M4의 T4.3)

**수용 기준:**
- 위젯을 끌면 손가락을 따라오고 미리보기가 셀에 붙는다
- 다른 위젯 위로 끌면 무효 표시가 나고, 놓으면 제자리로 돌아온다
- 격자 밖으로 끌면 경계에서 멈추거나 무효 표시가 난다

---

## T6.3 — 크기 조절

- [ ] 편집 모드에서만 크기 핸들을 노출. 우하단 하나로 시작한다 — 네 모서리 전부는
      과하고, 폰에서 핸들이 서로 붙어 누르기 어렵다.
- [ ] 핸들 터치 목표를 실제 그림보다 크게 잡는다(투명 여백)
- [ ] 드래그량을 셀 단위 크기로 환산
- [ ] `minSize`·`maxSize`(M4의 정의)로 자른다
- [ ] 격자 경계로 자른다
- [ ] 다른 위젯과 겹치면 무효 — 이동과 같은 규칙
- [ ] 손을 떼면 확정

**수용 기준:**
- Test 위젯을 1×1부터 격자 전체 크기까지 자유롭게 조절할 수 있다
- 최소 크기 아래로는 줄어들지 않는다
- 다른 위젯을 침범하는 크기로는 확정되지 않는다

---

## T6.4 — 제거

- [ ] 편집 모드에서 위젯마다 제거 버튼 — 홈화면 관용대로 좌상단
- [ ] 터치 목표 44px 확보
- [ ] 되돌릴 수 없으므로 확인을 받을지 결정 (M5 열린 질문 3과 함께)

---

## T6.5 — 키보드 조작

접근성은 M7에서 다루지만, **배치 조작의 키보드 대안은 여기서 만드는 편이 자연스럽다.**
포인터 로직과 같은 판정 함수를 쓰기 때문이다.

- [ ] 편집 모드에서 위젯에 초점을 줄 수 있다(`tabindex`)
- [ ] 방향키로 한 셀씩 이동
- [ ] `Shift` + 방향키로 한 셀씩 크기 변경
- [ ] `Delete`/`Backspace`로 제거
- [ ] 유효하지 않은 이동은 무시한다(포인터와 같은 판정)

이 조작이 되면 포인터 없는 환경에서도 쓸 수 있고, **자동 테스트가 훨씬 쉬워진다.**

---

## T6.6 — 판정 로직 테스트

포인터 처리는 테스트하기 어렵지만 **판정은 순수 함수**이므로 전부 검증한다.

- [ ] 이동 확정 판정 — `canPlaceAt(placement, others, metrics)`
- [ ] 크기 확정 판정 — 최소/최대/경계/겹침
- [ ] 픽셀 오프셋 → 셀 환산의 반올림 경계 (셀 중앙에서 넘어가는가)
- [ ] 자기 자신과는 겹침 판정을 하지 않는다 (흔한 실수)

**수용 기준:** 위 네 가지에 테스트가 있고, 특히 마지막 항목이 검증된다.

---

## 위험

1. **iOS 사파리의 제스처 가로채기.** 화면 가장자리에서 시작한 드래그를 브라우저가
   뒤로가기로 가져간다. 보드 가장자리에 여백을 두거나 `touch-action`으로 대응해야
   할 수 있다. 실기 확인이 필요하다 — 헤드리스로는 안 잡힌다.
2. **`pointercancel`이 잦은 환경.** 안드로이드 일부 브라우저에서 스크롤 판정이
   개입한다. `touch-action: none`이 제대로 걸렸는지 확인.
3. **좌표 반올림 누적.** 드래그 중 `transform`과 확정 후 절대 위치가 1~2px 어긋나
   깜빡이는 현상. 확정 시 트랜지션으로 가려지지만 근본은 M2의 소수점 처리다.
