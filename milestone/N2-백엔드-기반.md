# N2 — 백엔드 기반 (Supabase)

**여기부터 서버가 필요하다.** 스키마·RLS 정책을 세우고, N1이 만든 빈 세션 자리에
진짜 인증을 끼운다.

선행: N1 · 정본: [`../SPEC.md`](../SPEC.md) 4.2 / 6.1 · 전체 그림: [N0](./N0-네트워킹-설계.md)

> **2026-08-05 — 백엔드를 정했다.** 이 문서는 원래 *N2 — PocketBase 기반*이었고
> 라즈베리파이 자가호스팅을 전제로 쓰여 있었다. 아래 '왜 Supabase인가'에 뒤집은
> 이유를 남긴다. 이전 판의 판단 근거는 git 이력에 있다.

---

## 왜 Supabase인가

**먼저 정책이 있고 제품은 그 안에서 골랐다.**

> **우리가 돌볼 서버를 두지 않는다.** 기계도, VPS도, 컨테이너도 우리 손으로
> 돌리지 않는다. 서버 쪽 필요는 관리형 서비스로만 채운다. (SPEC 4.2 · CLAUDE.md
> 절대 원칙 4)

이유는 둘이다. **둘째가 더 중요하다.**

**1. 위 정책.** 라즈베리파이를 세우면 정전·DDNS·인증서·재부팅·백업이 전부 우리
몫이 되고, 그중 하나가 고장나면 판이 멈춘다. 글룸헤이븐은 한 판에 서너 시간짜리다.
**PocketBase가 탈락한 것은 제품이 나빠서가 아니라 관리형 선택지가 아예 없어서다** —
그 제품을 고르면 기계가 딸려온다.

**자가호스팅은 되돌아갈 길로도 두지 않는다.** Supabase는 오픈소스라 자가호스팅이
되지만 택하지 않는다. "언제든 옮길 수 있다"고 적어두면 그것이 곧 계획이 된다.

**2. Broadcast가 SPEC 5.4를 절충 없이 지킨다.** SPEC 5.4는 전투 상태에 대해
"끝나면 **어느 기기에도 남지 않는다**"고 못박았다. PocketBase에서는 값을 공유하려면
일단 테이블에 써야 해서, **써 놓고 지우는 절충**이 필요했다. Supabase Broadcast는
애초에 저장하지 않고 지나가는 메시지다 — 저장하지 않는 것이 기본값이면 실수로 남을
일도 없다.

**부하는 애초에 기준이 아니었다.** 한 판에 메시지 2,000건, 동시 연결 4개, 저장은
메가바이트 단위다. 무료 한도의 1%도 쓰지 않는다.

치르는 값은 **무료 등급의 일시정지(약 1주일)** 하나이며, 정책상 답은 **돈으로
치르는 쪽**으로 기운다. 아래 열린 질문 참조.

---

## 목표

1. Supabase 프로젝트가 서고, 스키마가 **마이그레이션 파일로** 관리된다.
2. **RLS가 서버에서 강제된다.** 클라이언트를 우회해도 남의 것이 안 보인다.
3. N1의 세션 자리에 `supabase-js`가 들어간다.
4. 아이디 로그인과 비밀번호 분실 경로가 정해진다.

---

## 왜 서버 규칙이 전부인가

레포와 번들이 공개다. 누구든 번들을 읽고 API를 직접 두드릴 수 있다. **클라이언트의
게이트는 "안 보여주기"일 뿐이고, "안 주기"는 서버만 할 수 있다.**

그래서 이 마일스톤의 진짜 산출물은 화면이 아니라 **정책 표**다. 각 테이블마다
누가 무엇을 할 수 있는지 적고, 그것을 그대로 시험한다.

**가장 조심할 곳: RLS를 켜지 않은 테이블은 `anon` 키만으로 통째로 열린다.**
테이블을 만들 때마다 정책보다 RLS 활성화가 먼저다.

## 할 일

### 프로젝트 세우기

- [ ] Supabase 프로젝트 생성. 지역은 가까운 곳으로 — 탭 반응에 왕복이 실린다.
- [ ] **`anon` 키와 `service_role` 키를 가른다.** 번들에 들어가도 되는 것은 `anon`뿐이다. `service_role`은 RLS를 우회하므로 클라이언트·레포·CI 로그 어디에도 두지 않는다.
- [ ] 로컬 개발 환경(`supabase start`)과 원격을 같은 마이그레이션으로 맞춘다.
- [ ] **백업.** 동기화가 붙으면 서버가 유일한 사본이 되는 순간이 오고, 그때가 위험하다. 관리형이라고 백업이 저절로 되는 것은 아니다 — 무료 등급의 보존 기간을 확인하고 부족하면 주기적으로 내려받는다.
- [ ] 운영 문서를 남긴다 — 어디에 무엇이 있고, 죽으면 어떻게 살리고, **비밀번호 분실 시 어떻게 하는지.**

### 스키마

레코드 단위와 이름만 정하고, 필드는 각 마일스톤에서 채운다.

- [ ] `profiles` — `auth.users`에 딸린 표시 이름 등. 아이디 로그인 방식이 정해진 뒤 채운다.
- [ ] `parties` — 이름, 만든 사람, 만든 때.
- [ ] `party_members` — 파티 × 사용자. **한 사람이 여러 파티에 속한다.**
- [ ] `invites` — 파티, 토큰, 만든 사람, 만료, 취소 여부, 쓴 횟수.
- [ ] `battles` — 파티, 연 사람, 연 때, 끝난 때.
- [ ] `battle_participants` — 전투 × 사용자.
- [ ] 마이그레이션 파일로 버전 관리. 손으로 만든 스키마는 재현되지 않는다.

**`battle_state` 테이블은 만들지 않는다.** 이전 판에는 "전투당 하나, 원소 여섯 값"
으로 적혀 있었다. 원소 상태는 **Broadcast로 흘려보내고 아무 데도 쓰지 않는다**
(SPEC 4.2 / 5.4). 방과 참여자는 서버가 알아야 하므로 테이블에 남지만, 값은 남지
않는다.

### 접근 규칙 — 이 마일스톤의 핵심

각 테이블에 대해 **표로 먼저 적고** 그대로 정책으로 옮긴다.

- [ ] **모든 테이블에 RLS를 켠다.** 정책을 쓰기 전에 이것부터.
- [ ] 로그인하지 않으면 **아무것도** 못 읽는다.
- [ ] 파티는 **속한 사람만** 읽는다.
- [ ] 초대는 **토큰을 아는 사람만** 쓸 수 있고, 목록으로는 못 읽는다.
- [ ] 전투는 **그 파티 사람만** 읽는다.
- [ ] 남의 파티 id를 넣어 만들기를 시도하면 막힌다.
- [ ] **Realtime 채널도 인가를 건다.** 테이블 정책을 아무리 잘 짜도 채널이 열려 있으면 남의 전투를 엿들을 수 있다. Broadcast는 테이블을 거치지 않으므로 **RLS가 대신 막아주지 않는다** — 여기가 새로 생긴 구멍이다.

### 클라이언트 붙이기

- [ ] `supabase-js` 도입. N1이 만든 `AuthAdapter` 경계 **안쪽만** 갈아끼운다. 화면과 스토어는 백엔드가 무엇인지 몰라야 한다.
- [ ] 프로젝트 주소와 `anon` 키는 `VITE_*`로. 공개해도 되는 값이므로 감추지 않는다 — 다만 `mock` 빌드에는 넣지 않는다(SPEC 3.1).
- [ ] 토큰 갱신은 **틈틈이, 실패해도 조용히.** 갱신 실패로 로그아웃시키면 오프라인에서 앱이 닫힌다.
- [ ] 401을 만나면 그때 세션을 버린다. 네트워크 오류와 구별한다 — 신호가 없는 것과 쫓겨난 것은 다르다.

---

## 검증

- [ ] 로그인하지 않은 채 API를 직접 호출하면 전부 거부된다. **브라우저가 아니라 `curl`로** 확인한다 — 화면을 안 거치는 것이 요점이다.
- [ ] 다른 파티 사람의 토큰으로 남의 파티를 읽으면 거부된다.
- [ ] 전투 참여자가 아닌 사람이 그 전투의 Broadcast 채널을 구독하면 거부된다.
- [ ] **RLS가 켜지지 않은 테이블이 하나도 없다.** 눈으로 세지 말고 질의로 확인한다.
- [ ] 번들에 `service_role`이 없다(`grep`).
- [ ] 서버를 끄고(또는 비행기 모드로) 앱을 열면 **저장된 세션으로 열린다.**

## 열린 질문

- **아이디 로그인을 Auth에 어떻게 앉힐 것인가.** 우리는 이메일로 로그인하지 않기로
  했는데(SPEC 4.2) Supabase Auth는 이메일·전화를 기준으로 삼는다. 합성 이메일을
  쓰는 길, 별도 신원 테이블을 두는 길 등이 있고 각각 **비밀번호 분실 경로**가
  달라진다. 둘을 함께 정한다.

  PocketBase 시절의 답("SMTP가 없으니 관리자가 콘솔에서 바꿔준다")은 **그 전제에서
  나온 것이라 그대로 옮겨오면 안 된다.** Supabase에는 메일 경로가 있으나 이메일로
  로그인하지 않으면 쓸 수 없다.

- **일시정지(약 1주일)를 어떻게 견딜 것인가.** 판이 뜸한 기간에 프로젝트가 잠들면
  다음 판의 첫 로그인이 실패한다. 갈래는 둘이다.

  | | 값 | 걸리는 것 |
  |---|---|---|
  | GitHub Actions 주간 핑 | 무료 | **우리가 만들어 돌볼 부품이 하나 는다** |
  | 유료 등급 | $25/월 | 문제 자체가 사라진다 |

  핑은 서버가 아니므로 정책을 어기지는 않는다. 다만 **조용히 고장나면 다음 판의
  첫 로그인이 실패하고, 고장을 알아채는 일까지 우리 몫이 된다.** 정책의 "값은
  돈으로 치른다"가 유료 쪽으로 기울인다 — 월 $25가 그 값어치를 하는지만 판단하면
  된다.

- **정식 배포를 어디에 올릴 것인가.** `anon` 키가 공개해도 되는 값이라 "정식을 열면
  GitHub Pages를 내린다"의 근거가 사라졌다(SPEC 3.1). **한 곳만 살린다는 원칙은
  유지**하되 그 한 곳을 정한다.

- **토큰 수명과 N1의 세션 만료를 어떻게 맞출 것인가.** N1은 30~90일 사이로 열어뒀다.

- **동시 접속 수.** 라즈베리파이 한 대를 걱정하던 질문이었으나 관리형으로 옮기며
  성격이 바뀌었다. 이제는 기계가 아니라 **무료 등급의 동시 연결 한도**를 본다 —
  N3의 초대 정책과 직결된다.
