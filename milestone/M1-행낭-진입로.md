# M1 — 행낭 진입로

웰컴 화면에서 행낭으로 들어가는 길을 뚫고, 빈 보드 셸을 세운다.
아직 격자도 위젯도 없다. **들어가고 나오는 것만 확실히 되게 한다.**

**선행:** M0 (라우트 테이블)
**예상 산출물:** `src/features/satchel/SatchelPage.tsx`, `SatchelPage.css`

---

## T1.1 — 카드 II 활성화

현재 두 카드는 `<li>` 안의 텍스트일 뿐 누를 수 없다.

- [ ] 카드 II를 링크로 만든다. 카드 전체가 누르는 영역이어야 한다 — 폰에서 제목
      글자만 누르게 하면 못 쓴다.
- [ ] `채비 중` 칩을 카드 II에서 제거한다.
- [ ] 카드 I은 **그대로 둔다.** 축 ①은 아직 없으므로 `채비 중`을 유지한다.
- [ ] 두 카드의 생김새가 갈린다 — 하나는 누를 수 있고 하나는 아니다. 이걸 시각적으로
      구분해 준다. 누를 수 있는 카드에만 hover/active 반응과 커서를 준다.

**주의 — 칩이 사라지면 레이아웃이 깨진다.** 현재 상태 칩은 `margin-top: auto`로
카드 바닥에 붙어 두 카드의 높이를 맞추고 있다. 칩을 지우면 카드 II의 아래쪽이
비어 정렬이 어긋난다. 칩 자리에 **진입을 알리는 요소**(예: `들어가기 →`)를 넣어
같은 자리를 채우는 편이 낫다.

**수용 기준:**
- 카드 II의 아무 곳이나 눌러 행낭으로 간다
- 카드 II에 `채비 중`이 없다
- 두 카드 높이와 바닥 요소 위치가 여전히 맞는다 (데스크톱에서 같은 y좌표)
- 키보드 `Tab`으로 카드 II에 초점이 가고 `Enter`로 들어간다

## T1.2 — 라우트와 지연 로드

- [ ] `#/satchel` 라우트를 M0의 라우트 테이블에 등록
- [ ] `SatchelPage`를 `lazy`로 분리한다. 웰컴 번들에 격자·제스처 코드가 섞이면
      첫 화면이 무거워진다. 고지 페이지에서 쓴 방식과 같다.
- [ ] 로딩 중 `Suspense` 폴백 — 고지 페이지는 `null`을 썼지만 행낭은 청크가 더
      클 수 있으므로 최소한의 자리 표시를 검토한다

**수용 기준:** 빌드 결과에 `Satchel` 청크가 따로 잡히고, 웰컴 번들 크기가 유의미하게
늘지 않는다.

## T1.3 — 보드 셸

위젯이 놓일 화면의 뼈대. 이 단계에서는 빈 영역이다.

- [ ] 전체 화면 레이아웃 — 툴바 영역과 보드 영역을 나눈다. 툴바는 M5에서 채우므로
      지금은 자리만 잡고 돌아가기 링크 하나만 둔다.
- [ ] **보드 영역이 스크롤되지 않게 한다.** 격자는 화면에 꽉 차야 하고 위젯은 그 안에
      들어간다. 홈화면처럼 페이지 넘김이 필요해지면 그때 다룬다(현재 범위 밖).
- [ ] `100dvh`와 `env(safe-area-inset-*)` 적용 — 웰컴 화면과 같은 규칙
- [ ] 가로/세로 회전 시 영역이 다시 계산되는지 확인

**수용 기준:**
- 폰 세로·가로, 태블릿, 데스크톱에서 보드 영역이 화면을 채우고 스크롤바가 없다
- 노치·홈 인디케이터를 침범하지 않는다
- 돌아가기로 웰컴에 복귀한다

---

## T1.4 — 화면 회전과 크기 변화 감지

M2의 격자 계산이 붙을 자리를 미리 마련한다.

- [ ] 보드 영역의 실제 픽셀 크기를 관측한다. `window.resize`만으로는 부족하다 —
      툴바 위치가 바뀌면(M5) 창 크기는 그대로인데 보드 영역만 달라진다.
      `ResizeObserver`로 보드 요소를 직접 관측한다.
- [ ] 관측값을 상태로 노출한다. M2가 이 값을 받아 격자를 계산한다.
- [ ] 리사이즈 폭주를 막는다 — 회전 중 연속 호출되므로 프레임 단위로 묶는다.

**수용 기준:** 창 크기를 바꾸거나 기기를 회전시키면 관측된 보드 크기가 따라 바뀌고,
콘솔에 과도한 호출이 찍히지 않는다.

---

## 검증 방법

헤드리스 브라우저로 확인한다. `--window-size`는 뷰포트를 바꾸지 못하므로
CDP `Emulation.setDeviceMetricsOverride`를 쓴다 — 이 함정에 한 번 빠진 적 있다.

- 375×667, 393×852, 852×393, 820×1180, 1440×900
- 각 크기에서 `document.documentElement.scrollWidth === innerWidth` (가로 넘침 없음)
- 보드 영역 높이가 뷰포트 안에 들어오는지

## 열린 질문

1. 카드 I도 언젠가 활성화된다. 그때 두 카드 모두 링크가 되면 지금 넣은 "누를 수 있는
   카드" 스타일이 기본값이 된다. 지금부터 링크 스타일을 기본으로 두고 카드 I만
   비활성 처리하는 편이 나을 수 있다.
2. 행낭에서 뒤로 가기 — 브라우저 뒤로가기로 충분한가, 화면에 돌아가기를 둘 것인가.
   플레이 중 폰 전체화면이면 브라우저 UI가 안 보일 수 있으므로 화면에 두는 쪽으로
   기울지만, 툴바 햄버거 메뉴(M5)에 넣는 방법도 있다.
