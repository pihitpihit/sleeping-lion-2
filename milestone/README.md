두 갈래다.

  위젯 편집 화면의 조작감을 기준으로 삼는다. M0~M9로 끝났다.

## 핵심 설계 결정

### 결정 1 — 레이아웃은 영속, 위젯 내부 상태는 휘발

**SPEC 5.2와 충돌하는 지점이라 먼저 정리한다.** SPEC은 인게임 도구에 "영속 저장
없음"을 못박았지만, 위젯 배치까지 휘발시키면 열 때마다 다시 배치해야 하므로 도구로
쓸 수 없다. SPEC 5.2가 이미 예외 후보(보정 덱 구성)를 두고 "**사용자 설정이지
캠페인 데이터가 아니다**"라고 성격을 구분해 놓았으니, 그 선을 그대로 따른다.

| 무엇 | 성격 | 저장 | 근거 |
|---|---|---|---|
| 위젯 배치(어떤 위젯이 어디에 얼마 크기로) | 사용자 설정 | **localStorage** | 매번 다시 하면 도구가 아니다 |
| 툴바 위치, 기본 모드 | 사용자 설정 | **localStorage** | 위와 같음 |
| 뽑은 보정 카드, 원소 하강 상태, 주도권 입력값 | 도구 런타임 | **메모리** | SPEC 5.2 그대로. 새로고침 시 초기화가 의도된 동작 |

**IndexedDB(Dexie)에 넣지 않고 서버로 동기화하지 않는다.** 이 둘은 축 ①의 것이다.
localStorage를 쓰는 이유는 성격이 다르다는 신호이기도 하다 — 캠페인 데이터와 같은
곳에 두면 나중에 실수로 동기화 대상에 섞인다.

### 결정 2 — 격자 라이브러리를 쓰지 않고 직접 만든다

react-grid-layout 같은 라이브러리는 **자유형 대시보드**를 위한 것이라 우리에게 과하다.
우리 격자는 홈화면처럼 정사각 셀에 스냅되는 단순한 규칙이고, 필요한 것은 정확한
테마 제어와 터치 우선 제스처다.

직접 만들 때 얻는 것:

- **배치 로직을 순수 함수로 분리**할 수 있다. SPEC 4.1이 도메인 로직을 UI와 떼어
  Vitest로 검증하라고 요구하는데, 라이브러리를 쓰면 그 경계가 라이브러리 안으로
  숨는다.
- 번들이 작다. 축 ②는 플레이 중 폰으로 여는 화면이라 초기 로딩이 곧 사용성이다.
- Pointer Events 하나로 마우스·터치·펜을 함께 다룰 수 있어 구현 난이도가 낮다.

포기하는 것: 밀어내기(reflow) 애니메이션 같은 고급 상호작용. M6에서 **겹침 금지 +
놓을 수 없으면 원위치**로 시작하고, 밀어내기는 후순위로 남긴다.

### 결정 3 — 열 수마다 레이아웃을 따로 둔다

폰 세로(4열)에서 짠 배치를 태블릿 가로(8열)에서 그대로 쓸 수 없다. 한 벌을 늘려
쓰면 위젯이 뭉개지고, 매번 다시 짜게 하면 번거롭다.

**열 수를 키로 레이아웃을 저장한다.** 처음 보는 열 수로 들어오면 가장 가까운 기존
레이아웃에서 파생해 만들어 준 뒤, 그때부터는 독립적으로 편집된다. 상세 규칙은 M3.

### 결정 4 — 진입 시 항상 플레이 모드

행낭을 여는 이유는 쓰려는 것이지 꾸미려는 것이 아니다. 마지막 모드를 기억하면
편집 중 나갔다가 다음 판에 편집 모드로 열리는 일이 생긴다.

### 결정 5 — 경로는 `#/satchel`

SPEC 12장 열린 질문 8을 여기서 닫는다. 별도 경로로 두고 오버레이는 쓰지 않는다 —
플레이 중 폰으로 여는 전체 화면이므로 기록지 위에 겹칠 이유가 없다.

식별자는 영어로 둔다(`satchel`). 저장소의 다른 식별자(`sl2`, `welcome`, `notice`)와
결을 맞춘다. 화면에 보이는 이름만 **행낭**이다.

## SPEC 개정 필요

M0 착수 전에 반영한다. 문서가 코드와 어긋난 채로 진행하면 나중에 어느 쪽이 맞는지
알 수 없게 된다.

1. **5.2** — "위 3계층 어디에도 저장하지 않는다"를 고친다. 위젯 배치와 툴바 설정은
   localStorage에 저장하고, 도구 런타임 상태만 메모리에 둔다는 구분을 명시.
2. **1장 축 ②** — 도구가 셋으로 한정된다는 서술에 **위젯 보드**라는 담는 그릇이
   추가됨을 반영. Test 위젯은 개발용 스캐폴딩이며 셋 제한의 예외임을 적는다.
3. **12장 열린 질문 8** — 닫는다(결정 5).
4. **4.1** — 상태관리 Zustand 도입 시점을 M0으로 명시.

## 용어

계획서 전체에서 아래 낱말을 고정해 쓴다. 섞어 쓰면 논의가 흐려진다.

| 낱말 | 뜻 |
|---|---|
| **보드(board)** | 위젯이 놓이는 격자 화면 전체 |
| **셀(cell)** | 격자 한 칸 |
| **배치(placement)** | 위젯 하나의 위치와 크기 `{x, y, w, h}` (셀 단위) |
| **레이아웃(layout)** | 한 열 수에 대한 배치 목록 |
| **위젯 정의(definition)** | 레지스트리에 등록된 위젯 종류 |
| **위젯 인스턴스(instance)** | 보드에 실제로 놓인 하나 |

같은 종류의 위젯을 여러 개 놓을 수 있으므로 정의와 인스턴스를 구분한다.

## 완료 판정

전 마일스톤이 끝났을 때 아래가 모두 참이어야 한다.

- 웰컴 화면의 카드 II를 눌러 행낭에 들어간다. 채비 중 표시가 없다.
- 플레이 모드로 열리고 격자가 보이지 않는다. 툴바에는 햄버거와 편집 전환만 있다.
- 편집 모드로 바꾸면 격자가 나타나고 툴바에 위젯 토글이 펼쳐진다.
- Test 위젯을 켜서 놓고, 끌어 옮기고, 격자에 맞춰 크기를 바꿀 수 있다.
- 플레이 모드로 돌아가면 격자와 편집 핸들이 사라지고 위젯은 그대로 있다.
- 새로고침해도 배치가 유지된다.
- 폰 세로·폰 가로·태블릿·데스크톱에서 각각 적절한 열 수와 툴바 위치로 열린다.
- 배치 로직 순수 함수에 Vitest 테스트가 있다.
